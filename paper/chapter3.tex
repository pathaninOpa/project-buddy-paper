\chapter{METHODOLOGY}
\hspace{\parindent} 
This section describes the methodology for developing the smart companion system for elderly care. The methodology comprises system design, data collection, pre-processing techniques, machine learning methods, hyperparameter configurations, and performance evaluation. The technical methods used in this study include speech recognition, natural language processing, sentiment analysis, and real-time video intercommunication. Each stage of the methodology is explained to ensure clarity and reproducibility.
%================= System Design =========================================
\section{System Design}
{ 
	\setlength{\leftskip}{1cm}
	\setlength{\parindent}{2.5em}
	The proposed smart companion system is designed to support elderly care by facilitating real-time emotional engagement, health monitoring, and seamless communication. The system architecture, illustrated in Figure 3.1, functions as a distributed ecosystem connecting the \textbf{Elderly User}, \textbf{Caretaker}, and \textbf{Cloud Backend}. The interaction begins with the \textbf{Tablet Application}, which captures the elderly user's voice and transmits it via API requests to a high-performance \textbf{gRPC server running on Google Compute Engine (GCE)}.
	\par
}
{ 
	\setlength{\leftskip}{1cm}
	\setlength{\parindent}{2.5em}
	Within this GCE infrastructure, the pipeline splits into synchronous and asynchronous flows. The synchronous path handles immediate interaction: \textbf{Local Faster-Whisper} transcribes speech to text, which is then processed by the \textbf{Local LLM Server (Gemma 3:4b on Ollama)} to generate a response. This response is converted to audio via \textbf{Google TTS} and streamed back to the tablet as a bot voice. Parallel to this, the transcribed text is routed to a dedicated \textbf{Sentiment Analysis} module (utilizing \textbf{gemma3:1b}). As shown by the green data flow in Figure 3.1, this module independently analyzes the text and uploads the results to the \textbf{Firebase Database}. The \textbf{Caretaker Mobile Application} connects to this ecosystem to fetch these sentiment results for the dashboard, schedule reminders (stored in Firebase and retrieved by the Tablet), and initiate \textbf{ZegoCloud Video Calls} directly with the tablet.
	\par
}

\noindent\textbf{Key Components:}
\begin{description}
    \item[\textbf{Care Receiver Application (Tablet):}] The \textbf{Care Receiver Application} is a Flutter-based interface designed specifically for elderly users, deployed on a tablet device. It serves as the primary touchpoint for interaction, featuring a simplified UI that displays the "Buddy" avatar. This application is responsible for capturing high-fidelity audio input via the device microphone and projecting the chatbot's voice and visual responses. It maintains a persistent connection to the backend to ensure real-time responsiveness for voice commands and queries.
    
    \item[\textbf{Caregiver Application (Mobile):}] The \textbf{Caregiver Application} provides family members with a dedicated mobile dashboard to monitor the elderly user's well-being. It allows caretakers to view longitudinal mood logs, receive alerts, and schedule medication or appointment reminders that are pushed to the tablet. Additionally, it integrates a signaling module to initiate peer-to-peer video calls, bridging the communication gap between the elderly and their family.
    
    \item[\textbf{Speech Recognition Engine:}] To convert spoken Thai into digital text, the system employs the \textbf{Faster Whisper} model. This engine is optimized for high-performance inference, ensuring high-accuracy transcription even in noisy environments. It processes raw audio frames to produce the `transcribedText` tokens that serve as the input for the cognitive pipeline.
    
    \item[\textbf{AI Inference Server:}] The core logic resides in a Python-based \textbf{AI Inference Server}, built using FastAPI and gRPC. This server acts as the orchestration layer, managing the tokenization of input text, maintaining conversation context windows, and routing requests to the appropriate model (LLM or Sentiment Analysis). It runs on Google Compute Engine (GCE) to leverage scalable compute resources for low-latency processing.
    
    \item[\textbf{Large Language Model (LLM):}] The cognitive reasoning is powered by the \textbf{GEMMA 3} family of models. \textbf{GEMMA 3:4b} functions as the primary conversational brain, generating contextually aware and persona-driven responses. In parallel, a lighter \textbf{GEMMA 3:1b} model is utilized for periodic emotion classification, analyzing text logs to extract sentiment trends without blocking the main conversational flow.
    
    \item[\textbf{Text-to-Speech (TTS):}] To provide a natural and empathetic user experience, the \textbf{Google Text-to-Speech API} is used to synthesize the chatbot's voice. The system employs the Neural2 model (`th-TH-Chirp3-HD-Charon`), which generates high-quality Thai speech with human-like prosody and intonation, converting the LLM's text output into an audible response.
    
    \item[\textbf{Video Call System:}] Real-time visual communication is facilitated by the \textbf{ZegoCloud SDK}. This component establishes a stable, low-latency peer-to-peer WebRTC connection between the tablet and mobile applications. It handles the complex signaling and media negotiation required to maintain high video quality, ensuring reliable face-to-face interaction.
    
    \item[\textbf{Database Systems:}] Data persistence is managed through a cloud storage architecture. \textbf{Firebase} is utilized for real-time data synchronization, handling user profiles, active reminders, and immediate status updates.
\end{description}

\section{Data}
{ 
	\setlength{\leftskip}{1cm}
	\setlength{\parindent}{2.5em}
	The system operates on multimodal data streams collected continuously during user interactions. This data is categorized into three primary modalities: Acoustic, Linguistic, and Visual, each serving a distinct role in the interaction loop.
	\par
}

\subsection{Acoustic Data (Voice Input)}
The primary input vector is the elderly user's spoken language. Raw audio is captured at a sampling rate of 16kHz via the tablet's microphone array. This data stream serves two purposes:
\begin{itemize}
    \item \textbf{Command Execution:} Immediate instructions (e.g., "Call my daughter") that trigger specific system functions.
    \item \textbf{Conversational Context:} Natural dialogue which is transcribed into text for downstream cognitive processing.
\end{itemize}

\subsection{Linguistic Data (Text \& Context)}
Once transcribed, the acoustic data is transformed into linguistic data (`transcribedText`). This includes:
\begin{itemize}
    \item \textbf{Current Utterance:} The immediate text input from the user ($U_t$).
    \item \textbf{Conversation History:} A sliding window of previous turns ($H_{t-k:t-1}$) maintained to provide context for the Large Language Model.
    \item \textbf{System Instructions:} Static persona definitions ($S$) that guide the agent's behavior.
\end{itemize}

\subsection{Visual Data (Real-time Communication)}
Visual data is captured exclusively during active video calls initiated by either the user or the caretaker. This stream is processed in real-time via ZegoCloud protocols and is \textbf{not} stored persistently, ensuring user privacy.

\subsection{Metadata \& Telemetry}
To support the caretaker's dashboard, the system logs metadata associated with each interaction event, including:
\begin{itemize}
    \item \textbf{Timestamps:} Precise time of interaction for trend analysis.
    \item \textbf{Emotion Tags:} The classified sentiment (e.g., "Happy", "Anxious") derived from the linguistic data.
    \item \textbf{Session IDs:} Unique identifiers to group interactions into daily or session-based buckets for longitudinal monitoring.
\end{itemize}

\subsection{Interactive Conversational Pipeline (STS Pipeline)}
{ 
	\setlength{\leftskip}{1cm}
	\setlength{\parindent}{2.5em}
	The system operates as a continuous cognitive loop comprising three subsystems: Perception, Cognition (Generative Core), and Actuation. This Speech-to-Speech (STS) pipeline, illustrated in Figure 3.1, ensures a natural and responsive interaction flow.
	\par
}

\subsubsection{Subsystem A: Multimodal Perception (The Ears)}
The Multimodal Perception subsystem serves as the sensory interface of the Buddy chatbot, tasked with bridging the physical and digital domains. Its primary objective is to transmit continuous, unstructured acoustic signals into discrete, semantically rich linguistic tokens that the downstream cognitive engine can process. Given the deployment context, for example, an elderly user's home, this subsystem must be robust against environmental challenges such as background noise (e.g., television, ambient chatter) and room reverberation. To achieve both high accuracy and computational efficiency on edge hardware, the architecture implements a three-tier processing cascade: an always-on low-power wake word detector, a spectral-based voice activity filter, and a high-fidelity Transformer-based transcription engine. This tiered approach ensures that heavy inference resources are only allocated when communicative intent is explicitly verified, optimizing the trade-off between responsiveness and power consumption.
\begin{itemize}
    \item \textbf{Wake Word Detection (Edge-AI):} To strictly minimize latency and privacy risks, the system remains in a dormant, low-power state until explicitly activated. This is managed by the \textbf{Picovoice Porcupine} engine, a highly efficient On-Device Wake Word detection system. Unlike cloud-based solutions that stream audio continuously, Porcupine processes the raw audio stream locally on the tablet's CPU using a specialized Recurrent Neural Network (RNN) trained on deep learning. It listens specifically for the custom keyword "Jao Buddy" (Hey Buddy). The engine computes a probability score for every incoming audio frame; only when this score exceeds a pre-configured sensitivity threshold (set to 0.7 to balance false positives and false negatives) does it trigger the downstream pipeline. This edge-based processing ensures that no audio data leaves the device until user intent is confirmed, preserving user privacy and optimizing bandwidth.
	\item \textbf{Audio Ingestion \& Voice Activity Detection (VAD):} Once the wake word is detected
	raw
	audio streams are captured from the microphone in 20-30ms frames ($x_n$). To filter out background 
	noise, a \textbf{WebRTCVAD} module processes these frames. The algorithm models the spectral energy
	of speech ($S$) and noise ($N$) using Gaussian Mixture Models (GMM). For each frame, it computes th
	log-likelihood ratio $\Lambda(x_n)$ to make a binary decision:
	\begin{equation}
	\Lambda(x_n) = \log \left( \frac{P(x_n | S)}{P(x_n | N)} \right) \gtrless \tau
	\end{equation}
	where $\tau$ is the decision threshold determined by the aggressiveness mode (Mode 1). If $\
	Lambda(x_n) > \tau$, the frame is classified as speech and passed to the transcription buffer; 
	otherwise, it is discarded as silence, significantly reducing the computational load on the 
	Transformer model.
	
	\item \textbf{Transcription (Transformer-based ASR):} The core transcription is handled by the 
	\textbf{Faster Whisper} model, a highly optimized implementation of OpenAI's Whisper, chosen for it
	accuracy and efficiency in Thai.
	\begin{itemize}
	\item \textbf{Architecture:} Whisper utilizes a Sequence-to-Sequence (Seq2Seq) Transformer 
	architecture. The input audio is first converted into a \textbf{log-Mel spectrogram}, a 
	two-dimensional representation that captures the spectral characteristics of sound over time.
	\item \textbf{Encoder-Decoder Mechanism:} The          's Encoder processes this spectrogra
	Transformer
	extracting robust acoustic features (phonemes, prosody). The Decoder then generates the text 
	transcription, predicting the probability of each subsequent text token based on the encoded acoust
	features and the previously generated tokens.
	\item \textbf{Optimization \& Quantization:} The "Faster" aspect comes from leveraging 
	\textbf{CTranslate2}, an inference engine that applies \textbf{8-bit integer quantization (int8)} t
	the model weights. This compression technique reduces the model's memory footprint and bandwidth 
	requirements. Consequently, the entire Transformer model can execute up to 4 times faster on 
	general-purpose hardware (like the GPU of the Raspberry Pi) compared to the original FP32 
	implementation, with negligible degradation in Word Error Rate (WER) for the target language.
	\end{itemize}
	\item \textbf{Text Normalization:} To mitigate hallucinations common in Transformer-based ASR during periods of 
	silence or background noise, the raw transcription $T$ is subjected to a linguistic validation filter. A language
	probability score $P_{\text{Thai}}(T)$ is computed as the ratio of valid Thai characters to the total character 
	count $N$:
	\begin{equation}
		P_{\text{Thai}}(T) = \frac{1}{N} \sum_{i=1}^{N} \mathbb{I}(c_i \in \mathcal{C}_{\text{Thai}})
	\end{equation}
	where $\mathcal{C}_{\text{Thai}}$ represents the Unicode range for Thai characters (U+0E00 to U+0E7F) and 
	$\mathbb{I}$ is the indicator function. The text is only accepted into the context window if $P_{\text{Thai}}(T) 
	\lambda$ (with $\lambda=0.5$), effectively filtering out non-speech artifacts and random English sentences noise.
\end{itemize}

\subsubsection{Subsystem B: Generative Cognition \& Reasoning (The Brain)}
This subsystem embodies the core intelligence of the Buddy robot, translating processed linguistic input into contextually relevant responses and purposeful actions. It operates through a sophisticated, multi-stage algorithmic process.

\paragraph{Stage I: State Construction \& Vectorization (Contextual Memory)}
Upon receiving transcribed text frames via \textbf{gRPC}, the system reconstructs the conversational state for the Large Language Model. To maintain coherence across turns without exceeding the model's token limit, a sliding window mechanism is employed. For any given turn $t$, the input context vector $C_t$ is formally defined as:
\begin{equation}
    C_t = S \oplus H_{t-k:t-1} \oplus U_t
\end{equation}
Where:
\begin{itemize}
    \item $S$ represents the immutable system persona instructions (e.g., "You are Buddy, an AI assistant for the elderly..."), guiding the model's overall behavior.
    \item $H_{t-k:t-1}$ denotes the sliding window history of the last $k$ conversational turns (where $k$ is dynamically determined but capped at 4096 tokens to fit the GEMMA 3:4b architecture's context window, utilizing techniques like Rotary Positional Embeddings or RoPE for sequence awareness).
    \item $U_t$ is the current user utterance, the immediate input requiring a response or action.
\end{itemize}

\paragraph{Stage II: Semantic Routing \& Intent Recognition (Decision Engine)}
Once the context $C_t$ is established, the \textbf{gemma3:4b} model functions as a semantic router, assessing the user's intent to determine if a specific external function (Tool Calling) is required or if a natural language response is sufficient. The system evaluates the probability $P$ of a reserved tool-trigger token against a predefined schema of available tools $\mathcal{T} = \{T_{reminder}, T_{call}\}$. The decision logic for the model's subsequent action is formally governed by:
\begin{equation}
    \text{Action}_t = \begin{cases} 
    \text{Execute } T_i & \text{if } \text{argmax}(P(w_0|C_t)) \in \mathcal{T} \\
    \text{Generate Response} & \text{otherwise}
    \end{cases}
\end{equation}
Where $\text{argmax}(P(w_0|C_t))$ represents the most probable next token given the current context. If this token signifies a tool call (e.g., a special `<|tool\_code|>` token), the standard text generation pipeline is paused. The corresponding Python function (e.g., `initiate\_video\_call()`) is executed, and its return value $R_i$ (e.g., "Call initiated successfully") is injected back into the context for a subsequent inference cycle. This allows the model to confirm actions verbally, grounded in the real-world outcome of the executed tool.

\paragraph{Stage III: Persona-Conditioned Synthesis (Response Formulation)}
In the event that no tool execution is deemed necessary, the \textbf{gemma3:4b} model proceeds to generate a conversational response. This synthesis process is meticulously conditioned on the pre-defined persona constraints. The system prompt ($S$) acts as a "soft constraint," guiding the LLM to enforce a "family-like" tone while explicitly suppressing robotic boilerplate (e.g., "As an AI language model...") and overly formal Thai particles (e.g., `Ka/Krub`) in favor of natural, casual sentence structures. While explicit emotion classification is handled asynchronously, the model's self-attention mechanism implicitly attends to the sentiment within the user's text ($U_t$), allowing it to naturally modulate its lexical choice (e.g., offering comfort in response to keywords indicating distress) to maintain an empathetic dialogue flow. 

\subsubsection{Subsystem C: Actuation \& Response (The Voice/Actions)}
The abstract outputs from the cognitive core are translated into tangible, user-perceptible actions, completing the interactive loop by providing verbal feedback or executing requested tasks.

\begin{itemize}
    \item \textbf{Verbal Actuation (Neural TTS):} When the cognitive core generates a text-based conversational response, this text is forwarded to the \textbf{Google Text-to-Speech (TTS) API}. The system specifically utilizes the Neural2 model with the `th-TH-Chirp3-HD-Charon` voice. This advanced neural network-based TTS system, leveraging architectures similar to \textbf{WaveNet}, synthesizes raw audio waveforms from text by modeling the nuances of human speech, including prosody (rhythm, stress, intonation). This ensures that the chatbot's verbal responses are not only clear and intelligible but also possess a natural, human-like quality, significantly enhancing the user's perception of companionship.
    \item \textbf{Functional Actuation:} If the cognitive core (Subsystem B, Stage II) determines that a tool execution is required based on user intent, the system performs the corresponding physical or digital action. Additionally, separate background processes manage long-term data analysis:
    \begin{itemize}
        \item \textbf{Asynchronous Mood Summary Generation:} Unlike immediate response generation, emotion tracking operates on a periodic schedule. A dedicated background script runs every 15 minutes, triggering the \textbf{gemma3:1b} model to analyze the accumulated `transcribedText` logs. This batch process classifies the user's emotional state into discrete categories (e.g., [Neutral, Happy, Relax, Sad, Pain, Anxiety, Angry]) and updates the `emotion\_history` in the Firebase database. This decoupling ensures that computationally intensive emotion trending does not introduce latency into the real-time conversation loop.
        \item \textbf{Reminder System:} Facilitates the scheduling and management of reminders by caretakers via their mobile application. These reminders are synchronized with the backend, and at the designated time, the chatbot audibly announces them to the elderly user, leveraging the Text-to-Speech system for clear delivery.
        \item \textbf{Caretaker Call Initiation:} Enables elderly users to directly initiate a video call to their registered caretaker. Upon detecting a specific voice command (e.g., “Call grandchild”) and confirming intent, the system activates the \textbf{ZegoCloud SDK} to establish a stable, low-latency video communication channel, thereby providing an immediate and direct connection.
    \end{itemize}
\end{itemize}

\section{Performance Evaluation}

The performance of the smart companion system will be evaluated based on the following metrics:

\subsection{Emotion Recognition Accuracy}

Emotion recognition accuracy will be measured using standard classification evaluation metrics:

\begin{itemize}
	\item \textbf{Confusion Matrix}: A table comparing predicted emotions against actual labels. It consists of:
	\begin{itemize}
		\item \textbf{True Positive (TP)}: Correctly predicted positive instances.
		\item \textbf{False Positive (FP)}: Incorrectly predicted positive instances.
		\item \textbf{True Negative (TN)}: Correctly predicted negative instances.
		\item \textbf{False Negative (FN)}: Incorrectly predicted negative instances.
	\end{itemize}
	\item \textbf{Precision, Recall, and F1-Score}:
	\begin{itemize}
		\item \textbf{Precision} = $\frac{TP}{TP + FP}$
		\item Measures the proportion of correctly predicted positive instances among all predicted positive instances.
		\item \textbf{Recall} = $\frac{TP}{TP + FN}$
		\item Measures the proportion of correctly predicted positive instances among all actual positive instances.
		\item \textbf{F1-Score} = $2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$
		\item The harmonic mean of precision and recall, balancing both metrics.
	\end{itemize}
	\item \textbf{Overall Accuracy}:
	\begin{itemize}
		\item $\text{Accuracy} = \frac{TP + TN}{TP + TN + FP + FN}$
		\item Measures the overall correctness of the model by considering both positive and negative instances.
	\end{itemize}
\end{itemize}

\subsection{Dialogue Generation Quality}

The evaluation of the model's ability to generate coherent and relevant responses is primarily conducted using an "LLM-as-Judge" methodology, complemented by human evaluation. This approach leverages a superior language model to assess the semantic quality of generated text, which correlates better with human judgment than traditional n-gram metrics.

\begin{itemize}
	\item \textbf{LLM-as-Judge (Gemini-2.5-Flash)}:
	\begin{itemize}
		\item A high-capability cloud model serves as the evaluator for responses generated by the local \textbf{Gemma 3:4b} model.
		\item \textbf{Scoring Scale}: Responses are rated on a scale of 1-10.
		\item \textbf{Evaluation Dimensions}:
		\begin{itemize}
			\item \textbf{Clarity}: Measures linguistic correctness and ease of comprehension.
			\item \textbf{Relevance to Elderly}: Assesses the appropriateness of the tone and content for the target demographic.
			\item \textbf{Conciseness}: Evaluates the efficiency of information delivery, prioritizing brevity for audio output.
		\end{itemize}
	\end{itemize}
	\item \textbf{Human Evaluation}:
	\begin{itemize}
		\item \textbf{Mean Opinion Score (MOS)}: Human participants rate interactions on a 1-5 scale.
		\item \textbf{Criteria}: Coherence, Fluency, Empathy, and Overall Satisfaction.
	\end{itemize}
\end{itemize}

\subsection{Speech-to-Text (STT) Performance}

The accuracy of the Thai speech-to-text module (Faster Whisper) will be evaluated using:

\begin{itemize}
	\item \textbf{Word Error Rate (WER)}:
	\begin{itemize}
		\item $\text{WER} = \frac{S + D + I}{N}$
		\item where $S$ = substitutions, $D$ = deletions, $I$ = insertions, and $N$ = total words in reference text.
	\end{itemize}
	\item \textbf{Character Error Rate (CER)}:
	\begin{itemize}
		\item $\text{CER} = \frac{S + D + I}{N}$
		\item where $N$ represents total characters in reference text, useful for Thai language without explicit word boundaries.
	\end{itemize}
\end{itemize}


\subsection{Video Call Quality}

The reliability and quality of the real-time communication feature, powered by the ZegoCloud SDK, are assessed against industry-standard benchmarks for telecommunication.

\begin{itemize}
	\item \textbf{Connection Success Rate}: The percentage of call attempts that successfully establish a peer-to-peer connection.
	\item \textbf{Average Latency}: The end-to-end delay (measured in milliseconds) between the audio/video capture on one device and its playback on the other. This is critical for maintaining a natural conversation flow.
	\item \textbf{Call Stability}: The ability of the system to maintain a continuous connection without drops or significant quality degradation over an extended period (e.g., >10 minutes).
	\item \textbf{Packet Loss Tolerance}: The system's resilience to network instability, specifically its ability to maintain audio intelligibility and video clarity despite packet loss.
\end{itemize}

\subsection{Software Testing and Validation}

To ensure the robustness and usability of the mobile application and backend services, a comprehensive testing strategy is employed, encompassing both functional and structural verification, as well as quantitative usability assessment.

\begin{itemize}
	\item \textbf{Black Box Testing}:
	\begin{itemize}
		\item \textbf{Functional Testing}: Verifies that all application features (e.g., login, call initiation, dashboard updates) function as specified in the requirements without knowledge of the internal code structure.
		\item \textbf{User Acceptance Testing (UAT)}: Real users from the target demographic perform typical tasks to validate the system's usability and effectiveness in real-world scenarios.
	\end{itemize}
	\item \textbf{White Box Testing}:
	\begin{itemize}
		\item \textbf{Unit Testing}: Validates individual components and functions (e.g., API endpoints, database queries) to ensure they produce correct outputs for given inputs.
		\item \textbf{Integration Testing}: Verifies that different modules (e.g., the mobile app and the API server) interact correctly and data flows seamlessly between them.
	\end{itemize}
	\item \textbf{System Usability Scale (SUS)}:
	\begin{itemize}
		\item A standardized 10-item questionnaire used to assess the perceived usability of the system.
		\item Participants rate each item on a 5-point Likert scale (1 = Strongly Disagree, 5 = Strongly Agree).
		\item The final score ranges from 0 to 100, providing a global measure of system usability, where a score above 68 is typically considered "above average".
	\end{itemize}
\end{itemize}
